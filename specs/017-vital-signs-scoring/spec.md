## Clarifications

### Session 2026-11-20

- Q: When a nurse tries to save a vital-signs reading for a patient whose status is "discharged", should the system refuse it or save it? → A: Refuse with 409 and a fixed message; nothing is saved. The reading history stays readable for discharged patients.
- Q: Should doctors also be allowed to enter vital-signs readings, or only nurses? → A: Nurses only. Doctors get 403, do not see the "Registrar signos vitales" button and see the nurses-only message on the entry page; any signed-in clinician may read the history.
- Q: How many readings should the reading history return, and in what order? → A: Newest first (ties: later saved first); 50 by default; an optional `limit` from 1 to 200, 422 outside that range.
- Q: Should a reading's time always be the server's clock at the moment it is saved, or may the nurse enter the time the vitals were actually taken? → A: Always the server's save time; a client-sent time is rejected with 422 as an unknown field; the form has no time field.
- Q: Should the form repeat the backend's value limits? → A: No. The form checks only filled fields, on oxygen and consciousness chosen, whole numbers and one decimal for temperature; range checks exist only in the backend (accepted limits, single source). On a 422 the form shows a fixed, translated message next to each field named in the problems (by parameter code) and a general message for problems that name no field, never a value, and keeps what was typed.

### Change request 2026-11-20 (manual check, after implementation)

- **CR1 — Risk band colors**: the risk band is shown as a badge like StatusBadge (soft background, solid border, icon, band name in dark text; color is never the only cue). One color per band, green → yellow → orange → red: `low` → stable tokens, `low-medium` → warning tokens, `medium` → two new tokens `--color-band-medium` (`#EA580C`, border and icon only, never text) and `--color-band-medium-soft` (`#FFEDD5`, background), `high` → critical tokens. The mapping lives in one frontend helper (`utils/bandStatus.js`) with unit tests and is recorded in D-50 and the glossary. `monitoring_status` keeps its own four values; US-02 decides how bands map to it (AC21, FR-023).
- **CR2 — Clearer validation messages**: each vital-sign problem in a 422 carries a `ctx` with the accepted rule from `ACCEPTED_LIMITS`, never the submitted value: `out_of_range` → `{"min", "max"}` (temperature as one-decimal strings), `not_allowed` → `{"allowed": [...]}`, `too_many_decimals` → `{"decimals": 1}`. The form shows a translated message per reason using `ctx` (for example "Debe estar entre 0 y 100 %." / "Must be between 0 and 100 %.", "Usa máximo un decimal." / "Use at most one decimal.", "Elige uno de: A, C, V, P, U." / "Choose one of: A, C, V, P, U.") and keeps the generic message when `ctx` is missing (AC22, FR-024).
- **CR3 — Number format**: decimals are shown with a comma in Spanish (`36,8`, `38,1–39,0`) and a dot in English (`36.8`, `38.1–39.0`) on the result view, in the reasons and in the range messages; input still accepts both (AC23, FR-025).
- Unchanged: `ACCEPTED_LIMITS`, the scoring module, `patients.py`, `simulator.py`; no new dependency.

## User Story *(mandatory)*

**Story ID**: US-03

**Type**: Functional (baseline)

**Story**: As a nurse, I want each vital-signs reading to be saved and scored with the reason for each point, so that I understand the patient's risk.

**Depends on**: TS-03 (tables and migrations), TS-06 (authentication), TS-07 (scoring module), TS-08 (simulator and `record_reading`), TS-12 (UI foundation), TS-13 (client routing). All merged. ### Acceptance Criteria

<!-- Each criterion must be testable. qa-tester writes at least one test per criterion. -->

1. **AC1 — Every reading is saved with its score**: **Given** a valid reading for a patient, **When** it is saved by any caller (the simulator, the new entry operation or any other code), **Then** exactly one stored score exists for that reading with the scoring system name (`NEWS2`), the NEWS2 score, the risk band and seven explanation entries, one per parameter in the standard parameter order, each holding the parameter code, the value, the points and the range that gave the points (inclusive low and high bound, either of which may be open) or, for on-oxygen and consciousness, the matched category values.
2. **AC2 — Stored score equals the scoring module**: **Given** any valid reading, **When** it is saved, **Then** its stored NEWS2 score, risk band and every entry are identical to what the current scoring system returns for the same values (the scoring module is the only place that knows NEWS2 rules).
3. **AC3 — All or nothing**: **Given** a reading, **When** the reading or its score cannot be saved (invalid values, a database error, or a failure while scoring), **Then** neither is stored: no reading without a score and no score without a reading.
4. **AC4 — Simulator readings are scored unchanged**: **Given** the existing simulator, **When** it runs a round, **Then** every reading it saves has a stored score, and the simulator's own code and output are unchanged.
5. **AC5 — Existing readings are scored once (backfill)**: **Given** a database with readings saved before this story, **When** the database is upgraded, **Then** every existing reading gets exactly one stored score computed by the current scoring system, readings created afterwards are scored on save, and after the upgrade no reading is without a score. Downgrading removes only the stored scores (they are derived from readings); upgrading again rebuilds them.
6. **AC6 — Demo reset still works**: **Given** the demo patients with readings and stored scores, **When** the demo patients are reset, **Then** their stored scores are deleted together with their readings, and the reset succeeds.
7. **AC7 — Nurse enters a reading**: **Given** a signed-in nurse and an existing, active patient, **When** they send a valid reading for that patient code, **Then** the system answers "created" (201) with the reading (`recorded_at` and the seven values) and its stored score (system, NEWS2 score, risk band and the seven explanation entries); `recorded_at` is the time the server saved it; no internal ids are returned.
8. **AC8 — Who may enter a reading**: **Given** a reading entry request, **When** it is sent signed out (no or invalid token), **Then** the answer is 401; **When** it is sent by a signed-in doctor, **Then** the answer is 403; in both cases nothing is stored.
9. **AC9 — Unknown or discharged patient**: **Given** a signed-in nurse, **When** they send a reading for a patient code that does not exist (or is not in the patient code format), **Then** the answer is 404 with a fixed message; **When** the patient's `status` is `discharged`, **Then** the answer is 409 with a fixed message; in both cases nothing is stored.
10. **AC10 — Input validation without echoing values**: **Given** a reading with a missing parameter, a value of the wrong type, a value outside the accepted limits, a temperature with more than one decimal, a consciousness code other than A, C, V, P or U, or an unknown extra field, **When** it is sent, **Then** the answer is 422 listing each problem as the parameter (or the unknown field name, cleaned and shortened) and the reason code, plus the accepted rule for `out_of_range`, `not_allowed` and `too_many_decimals` (AC22); it never repeats a submitted value, and nothing is stored.
11. **AC11 — Reading history**: **Given** any signed-in clinician (doctor or nurse), **When** they ask for the readings of an existing patient code, **Then** they get that patient's readings newest first, each with its stored score and entries, at most 50 by default and at most the requested number when a limit from 1 to 200 is given; signed out the answer is 401, an unknown patient code gives 404, and a limit outside 1–200 gives 422.
12. **AC12 — Entry page for nurses**: **Given** a signed-in nurse, **When** they open `/patients/<patient code>/readings/new`, **Then** they see a form inside a Card, titled with the patient code, with seven fields: respiratory rate, SpO2, on oxygen (yes / no), systolic blood pressure, heart rate, consciousness (ACVPU, the five codes with their meaning), and temperature (one decimal); nothing is pre-selected for on oxygen and consciousness, all seven fields are required, and there is no field for the time.
13. **AC13 — Form checks before sending**: **Given** the entry form, **When** the nurse submits it with a field empty, on oxygen or consciousness not chosen, a whole-number field holding something other than a whole number, or a temperature with more than one decimal, **Then** the form shows a message next to each invalid field, does not send the request, and keeps what was typed. The form does not check value ranges; those are checked only by the backend.
14. **AC14 — Result with the reason for each point**: **Given** a valid form, **When** the nurse submits it and the system answers "created", **Then** the page shows the stored result: the NEWS2 score, the risk band as a colored badge (AC21), and for each of the seven parameters its name, the value, the points and the reason (the range or category that gave the points, for example "21–24", "≤ 8", "≥ 25" or "C, V, P, U"); everything shown comes from the answer, the frontend never calculates points, the score or the band; the page offers to enter another reading and a link back to the patient detail page.
15. **AC15 — Validation error from the backend**: **Given** a submitted form, **When** the system answers 422, **Then** the page stays on the form, keeps what was typed, shows a fixed, translated message next to each field named in the problems (matched by parameter code; worded per reason with the accepted rule when the answer gives one, AC22), shows a fixed, translated general message for any problem that names no field of the form, never shows a submitted value or the raw server text, and the submit button is usable again.
16. **AC16 — Failed save keeps the form**: **Given** a submitted form, **When** the system answers with not found, conflict (discharged patient), a server error or no answer (network failure or timeout), **Then** the page stays on the form, keeps what was typed, shows a fixed, translated error message (never the raw server text), and the submit button is usable again; while a save is in progress the submit button is disabled so the reading cannot be sent twice.
17. **AC17 — Page protected and role-aware**: **Given** `/patients/<patient code>/readings/new`, **When** a signed-out visitor opens it, **Then** they are redirected to the login page (existing protected-route behavior); **When** a signed-in doctor opens it, **Then** they see a translated message that only nurses can record vital signs and a link back to the patient detail page, and no form.
18. **AC18 — Address ranking**: **Given** the app routes, **When** `/patients/<valid patient code>/readings/new` is opened, **Then** the entry page is shown, not the patient detail page or the not-found page; **When** the patient code in that address is not in the patient code format, **Then** the not-found page is shown.
19. **AC19 — "Registrar signos vitales" button for nurses only**: **Given** the patient detail page, **When** a nurse is signed in, **Then** a "Registrar signos vitales" ("Record vital signs") button with an icon is shown and opens `/patients/<patient code>/readings/new`; **When** a doctor is signed in, **Then** the button is not shown.
20. **AC20 — Spanish by default, English switch**: **Given** the entry page, the result and the button, **When** the language is Spanish (default) or English, **Then** every label, option, parameter name, risk band, reason, button and message is shown in that language using glossary terms, and switching language does not clear what was typed or the result shown.
21. **AC21 — Risk band badge (change request 2026-11-20)**: **Given** a stored result, **When** it is shown, **Then** the risk band appears as a badge with a soft background, a solid border, a decorative icon and the translated band name in the dark text color: `low` green (stable tokens), `low-medium` yellow (warning tokens), `medium` orange (`--color-band-medium` / `--color-band-medium-soft`), `high` red (critical tokens); each band has its own icon, so color is never the only cue; the dark text on `--color-band-medium-soft` is at least 4.5:1 and `--color-band-medium` against `--color-band-medium-soft` at least 3:1; an unknown band value shows the neutral no-data style with the label "Desconocida" / "Unknown".
22. **AC22 — Validation messages with the accepted rule (change request 2026-11-20)**: **Given** a reading with a problem, **When** the system answers 422, **Then** each `out_of_range` problem has `ctx` `{"min", "max"}` from the accepted limits (temperature as one-decimal strings), each `not_allowed` has `ctx` `{"allowed": [...]}`, each `too_many_decimals` has `ctx` `{"decimals": 1}`, other reasons have no `ctx`, and the body never contains a submitted value; **and** the form shows next to the field "Debe estar entre {min} y {max} {unidad}." / "Must be between {min} and {max} {unit}.", "Usa máximo un decimal." / "Use at most one decimal." or "Elige uno de: A, C, V, P, U." / "Choose one of: A, C, V, P, U.", and the generic "Valor no aceptado. Revisa el dato." / "Value not accepted. Check it." when `ctx` is missing or the reason is `wrong_type`; no submitted value appears on screen in these messages.
23. **AC23 — Number format by language (change request 2026-11-20)**: **Given** the result view, the reasons and the range messages, **When** the language is Spanish, **Then** decimals use a comma (`36,8`, `38,1–39,0`, "entre 25,0 y 45,0 °C"); **When** it is English, **Then** they use a dot (`36.8`, `38.1–39.0`); whole numbers are unchanged; the temperature input still accepts both a comma and a dot.

### Out of Scope

- The content of the patient list (US-02), alerts and re-triage suggestions (US-04) and the patient detail content (US-05). This story only adds a mounted nurse-only button to the patient detail placeholder.
- Editing or deleting readings, or entering a reading with a past time.
- Any scoring system other than NEWS2, and NEWS2 SpO2 Scale 2.
- Calculating NEWS2, points or the risk band in the frontend; it only displays what the backend stored.
- Changing the triage level or creating triage events or alerts from a score (US-04).
- Charts, export or deterioration prediction (US-06, US-10, US-08).

### Edge Cases

- **Boundary values** (for example respiratory rate 20 and 21, temperature 38.0 and 38.1, systolic 219 and 220): stored entries match the scoring module exactly, including which range was matched.
- **Open-ended ranges** (for example respiratory rate ≤ 8 or heart rate ≥ 131): the entry has no low or no high bound, and the page shows "≤ 8" or "≥ 131".
- **Out-of-range value typed in the form** (for example SpO2 `150`): the form sends it (it does not check ranges); the backend answers 422 with `ctx` `{"min": 0, "max": 100}` and the form shows "Debe estar entre 0 y 100 %." next to SpO2, without the value `150`, keeping what was typed.
- **A submitted value equal to a limit text** (for example SpO2 `100` is valid, but a test that sends `101` sees `100` in `ctx`): `ctx` holds only the limits, so tests that check "no submitted value is echoed" use values that differ from every limit.
- **Temperature sent as a whole number** (`37`): accepted and stored as `37.0`; `37.25` is rejected with 422 (`too_many_decimals`).
- **On oxygen sent as `"yes"`, `1` or `"true"`**: rejected with 422 (`wrong_type`); only a true/false value is accepted.
- **Numbers sent as text** (`"18"`) or with decimals where a whole number is expected (`18.5`): rejected with 422, values not echoed.
- **A client-sent `recorded_at`, patient code or score in the body**: rejected with 422 as an unknown field; the time and the score always come from the server.
- **Patient code in lower case or with other characters**: not in the patient code format, so 404 from the API and the not-found page in the app.
- **Patient discharged between opening the form and saving**: the save gets 409 and the nurse sees a translated "this patient is discharged" message; nothing is stored.
- **A patient with no readings**: the history answers an empty list, not an error.
- **Two readings saved in the same second for one patient**: both are kept; the history orders them newest first, with a stable tie-break (the later saved first).
- **Backfill on an empty database**: the upgrade succeeds and scores nothing.
- **An existing reading that no longer passes validation during the backfill** (not expected: all readings were saved through the validating `record_reading`): the upgrade stops with a clear error naming no values, and nothing is half-upgraded.
- **Session expires while the form is open**: the save gets a 401 and the existing session-expiry handling sends the nurse to the login page.
- **A doctor types the entry address directly**: no form is shown (AC17), and the server still refuses with 403 if a request is sent another way.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every reading MUST have exactly one stored score, saved in the same transaction as the reading. The stored score MUST hold the scoring system name, the NEWS2 score, the risk band, and seven explanation entries in parameter order, each with the parameter code, the value, the points, and the matched range (low and high bound, each possibly open) or the matched category values. Entries MUST hold codes and numbers only, never sentences.
- **FR-002**: `record_reading` MUST remain the only place that creates readings. It MUST validate the values, score them with the scoring system chosen by the scoring module (no NEWS2 rules outside the scoring module), and add both the reading and its stored score without committing (the caller commits or rolls back, as today). Its callers, including the simulator, MUST NOT need changes.
- **FR-003**: A database migration MUST add the storage for scores and, in the same upgrade, score every existing reading once with the current scoring system, so that after the upgrade every reading has exactly one stored score. Each reading MUST NOT be able to have more than one stored score. Its downgrade MUST remove only the score storage (readings are untouched). During the deploy of this story the simulator MUST NOT be run, because the migration runs before the new code is live and a reading saved by the old code would have no score.
- **FR-004**: The demo reset MUST delete the demo patients' stored scores before their readings (foreign keys are restrictive), and MUST keep working.
- **FR-005**: The system MUST offer a reading entry operation (`POST /api/patients/{patient code}/readings`) that saves one reading for the patient through `record_reading` and answers 201 with the reading (`recorded_at` and the seven values) and its stored score (system, NEWS2 score, risk band, entries). Internal ids (`patient_id`, reading id, score id) MUST NOT be returned.
- **FR-006**: The entry operation MUST require a signed-in user (401 otherwise) whose role is `nurse` (403 for any other role, with a fixed message that only nurses can record vital signs).
- **FR-007**: The entry operation MUST answer 404 with a fixed message for an unknown patient code or a code not in the patient code format, and 409 with a fixed message when the patient's `status` is `discharged`.
- **FR-008**: The entry operation MUST validate the body with the existing accepted limits and mapping validation of the scoring module (single source of the limits). Every validation problem MUST be answered with 422 listing parameter (or cleaned unknown field name), reason code and, where FR-024 says so, the accepted rule (`ctx`), never a submitted value, and nothing MUST be stored. Fields other than the seven parameters MUST be rejected.
- **FR-009**: `recorded_at` MUST be set by the server at save time; it MUST NOT be accepted from the client.
- **FR-010**: The system MUST offer a reading history operation (`GET /api/patients/{patient code}/readings`) for any signed-in user (401 otherwise) that answers the patient's readings newest first (ties: later saved first), each with its stored score and entries, limited to 50 by default or to an optional `limit` from 1 to 200 (422 outside that range, without echoing it); 404 for an unknown patient code. It MUST also answer for `discharged` patients. It MUST read stored scores and MUST NOT recompute them.
- **FR-011**: Error answers (401, 403, 404, 409, 422, and 503 when the database is unavailable, as in the existing endpoints) MUST use fixed, safe messages that reveal no internal details (no stack traces, database errors or submitted values).
- **FR-012**: The app MUST provide a protected page at `/patients/:identifier/readings/new`, inside the existing protected route group, that ranks above `/patients/:identifier` and the not-found page; a patient code not in the patient code format MUST show the not-found page.
- **FR-013**: For a signed-in nurse, the page MUST show a form inside the shared Card with the seven parameters: respiratory rate (breaths/min), SpO2 (%), on oxygen (yes / no, native radio inputs, nothing pre-selected), systolic blood pressure (mmHg), heart rate (beats/min), consciousness (the ACVPU codes A, C, V, P, U each with its meaning, nothing pre-selected), and temperature (°C, one decimal). All fields are required. The form MUST NOT ask for the time.
- **FR-014**: The form MUST check before sending only that every field is filled, that on oxygen and consciousness are chosen, that whole-number fields hold whole numbers and that temperature has at most one decimal; it MUST show a message next to each invalid field and MUST NOT send an invalid form. The form MUST NOT check value ranges: the accepted limits live only in the backend (single source). When the backend answers 422, the form MUST keep what was typed, show a fixed, translated message next to each field named in the problems (matched by parameter code; worded per reason with the accepted rule from `ctx` as in FR-024, otherwise the generic message), show a fixed, translated general message for any problem that names no form field (for example an unknown field), and MUST NOT show any submitted value or the raw server text.
- **FR-015**: The submit action MUST use the shared Button and be disabled while a save is in progress. On 201 the page MUST show the stored result from the answer: the NEWS2 score, the risk band as a badge (FR-023), and a row per parameter with its translated name, value, points and translated reason (range "low–high", "≤ high", "≥ low", or the category values; on oxygen and consciousness show their translated values), with numbers formatted as in FR-025. It MUST offer to enter another reading (clearing the form) and a link back to the patient detail page. The frontend MUST NOT compute points, the NEWS2 score or the risk band.
- **FR-016**: On 404, 409, 5xx or a network/timeout failure (422 is handled as in FR-014), the form MUST stay filled in and show a fixed, translated error message; on 401 the existing session-expiry handling applies.
- **FR-017**: For a signed-in doctor, the entry page MUST show a translated "only nurses can record vital signs" message with a link back to the patient detail page, and no form.
- **FR-018**: The patient detail page MUST show a "Registrar signos vitales" / "Record vital signs" button (shared Button, with an icon from the project's icon library, D-46) that opens `/patients/<patient code>/readings/new`, only when the signed-in user's role is `nurse`. It MUST be a small component mounted with one line on the page, so US-05 only has to keep that line.
- **FR-019**: Every UI text in this story MUST be in Spanish by default and English with the language switch, come from the translations file and use glossary terms. The glossary MUST gain the new terms in the same PR (at least: the stored score, the entry page, the "Registrar signos vitales" button, the seven parameter labels, the ACVPU labels, the risk band labels and the reason display).
- **FR-020**: All styling MUST use design tokens only (no raw colors outside `tokens.css`); the only new tokens are the two of FR-023; color MUST NOT be the only cue for the risk band (its text label and icon are always shown); existing raw-color and contrast guard tests MUST keep passing.
- **FR-021**: Automated tests MUST cover: storage and all-or-nothing; `record_reading` scoring, including the simulator path; the backfill; each API status (201, 401, 403, 404, 409, 422 without echoed values) and the history (order, default and given limit, empty list); the per-parameter entries at boundaries and open ends; and the page (nurse form, doctor message, client checks for filled fields, choices, whole numbers and one decimal only, per-field and general messages for a 422, result view in both languages, failed save, button visibility, route ranking). All existing tests MUST pass, and `pytest`, `npm test`, `npm run build` and `npm audit --audit-level=high` MUST pass.
- **FR-022**: The decision to store the score with each reading at save time (and read it instead of recomputing it), with entries as codes and numbers translated by the frontend, MUST be recorded as D-50 in `docs/DECISIONS.md`; `docs/BACKLOG.md` and `docs/PROJECT_STATUS.md` MUST show US-03 as done when the story is finished. D-50 MUST also record the change request of 2026-11-20 (band-to-color mapping and the two new tokens, amending D-43 in part; `ctx` in vital-sign 422s; number format by language) and the note that US-02 decides how risk bands map to `monitoring_status`.
- **FR-023** (change request 2026-11-20): The result view MUST show the risk band as a badge with a soft background, a solid border, a decorative `lucide-react` icon (one per band) and the translated band name in `--color-text`. The band-to-style mapping MUST live in one frontend helper (`frontend/src/utils/bandStatus.js`) with unit tests: `low` → `--color-stable` / `--color-stable-soft`; `low-medium` → `--color-warning` / `--color-warning-soft`; `medium` → `--color-band-medium` / `--color-band-medium-soft`; `high` → `--color-critical` / `--color-critical-soft`; any other value → `--color-no-data` / `--color-no-data-soft` with the label `riskBand.unknown`. `tokens.css` MUST gain `--color-band-medium: #EA580C` (border and icon only, never text) and `--color-band-medium-soft: #FFEDD5` (background); the contrast test MUST check `--color-text` on `--color-band-medium-soft` ≥ 4.5:1 (12.77:1) and `--color-band-medium` on `--color-band-medium-soft` ≥ 3:1 (3.11:1), and the token test MUST pin both values. `monitoring_status` and `StatusBadge` are unchanged.
- **FR-024** (change request 2026-11-20): Each problem in a vital-sign 422 MUST carry `ctx` built only from `ACCEPTED_LIMITS[parameter]` (never from the submitted value): `out_of_range` → `{"min": …, "max": …}` (integers as numbers; temperature as one-decimal strings `"25.0"`, `"45.0"`), `not_allowed` → `{"allowed": [...]}`, `too_many_decimals` → `{"decimals": <limit decimals>}`; `missing`, `unknown` and `wrong_type` have no `ctx`. The form MUST map `out_of_range` + `ctx` → `recordReading.rangeError` with min, max (formatted as FR-025) and the parameter's unit, `too_many_decimals` → `recordReading.decimalsError`, `not_allowed` + `ctx` → `recordReading.allowedError` with the values joined by ", ", `missing` → `recordReading.required`, and anything else or a missing `ctx` → `recordReading.valueRejected`. `ACCEPTED_LIMITS` and the scoring module MUST NOT change.
- **FR-025** (change request 2026-11-20): One frontend helper MUST format decimal numbers for display by language: comma in Spanish, dot in English; whole numbers unchanged. It MUST be used for values, reasons (ranges) and the range message; the temperature input keeps accepting both separators.

### Key Entities *(include if feature involves data)*

- **Reading** (existing `vital_signs` table, unchanged): one set of the seven parameters for one patient, with `recorded_at` set by the server.
- **Stored score** (new): the result of scoring one reading, exactly one per reading: scoring system name, NEWS2 score, risk band, and the seven explanation entries. Saved together with its reading; never edited.
- **Explanation entry** (part of the stored score; existing concept `ParameterScore`): for one parameter, its code, value, points and the matched range (low/high, possibly open) or category values. This is "the reason for each point".
- **Patient** (existing, unchanged): addressed by its patient code; only `active` patients accept new entered readings.
- **User** (existing): only the `nurse` role may enter readings; any signed-in user may read the history.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After the upgrade and after any simulator run, 100% of readings have exactly one stored score; 0 readings exist without one.
- **SC-002**: For 100% of the test readings, including every range boundary and open end, the stored score and entries equal the scoring module's result.
- **SC-003**: A nurse can enter a reading and see its NEWS2 score, risk band and the reason for every point in under 1 minute, without leaving the page.
- **SC-004**: 100% of entry attempts by doctors or signed-out callers are refused (403 / 401) and store nothing; 100% of entries for unknown or discharged patients are refused (404 / 409) and store nothing.
- **SC-005**: 100% of invalid inputs in the test cases are refused with 422 and 0 error answers contain a submitted value.
- **SC-006**: 100% of the texts on the entry page, the result and the button appear in Spanish by default and in English after switching; 0 raw colors are added outside `tokens.css` (guard test passes); the four risk bands show four distinct badge styles with an icon and a label, and every new color pair passes the contrast test.
- **SC-007**: All existing backend and frontend tests still pass, and every acceptance criterion has at least one automated test.

## Assumptions

- **Discharged patients**: entering a reading for a `discharged` patient is refused with 409, since a discharged patient is no longer monitored and the simulator already skips them. The history still answers for discharged patients (confirmed in Clarifications, 2026-11-20).
- **Who enters readings**: only nurses may enter readings, as in the backlog story and US-01; doctors may read the history (confirmed in Clarifications, 2026-11-20).
- **History limit and order**: newest first, default 50, optional `limit` 1–200; this is enough for the later detail page, chart and deterioration prediction without paging (confirmed in Clarifications, 2026-11-20).
- **`recorded_at`**: always the server's save time, as today (database default); entering a past time is out of scope (confirmed in Clarifications, 2026-11-20).
- The stored score keeps the scoring system name so that a future scoring system can be stored next to NEWS2 results without changing the shape; only NEWS2 is produced now.
- The backfill uses the scoring module at upgrade time. It is acceptable for the academic scope because existing readings are few and synthetic; the downgrade drops the stored scores, which upgrading again rebuilds.
- The frontend does not repeat the accepted limits: its checks cover only filled fields, choices, whole numbers and one decimal; range validation and scoring stay in the backend, and out-of-range values come back as a 422 shown next to the field (confirmed in Clarifications, 2026-11-20).
- The existing frontend API client, its 401 session-expiry handling and the signed-in user's role from `GET /api/me` are reused, as in US-01.
- Adding the nurse-only button to `PatientDetailPage` (a TS-13 placeholder) counts as mounting a component, which the constitution (Principle III) allows; US-05 keeps the mounted line when it replaces the page body.
- No real patient data is used; all readings are synthetic (constitution Principle VI).

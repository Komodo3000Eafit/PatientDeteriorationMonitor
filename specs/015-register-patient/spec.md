# Feature Specification: Register Patient

**Feature Branch**: `015-register-patient`

**Created**: 2026-11-20

**Status**: Draft

**Input**: User description: "Use feature number 015. US-01 (functional, baseline): As a nurse, I want to register a triaged patient with their initial triage level, so that the system starts monitoring them. Depends on TS-03, TS-06, TS-12, TS-13. Decisions already taken: (1) the patient code is generated by the system as the next free PAT-NNN starting at PAT-007, never PAT-001 to PAT-006 (reserved for the demo simulator), retrying once on a unique-code conflict; (2) the name field is required and labeled as fictitious (\"do not use real data\"); (3) only the nurse role may register (doctor gets 403, signed out 401), and the \"Register patient\" button on the patient list is shown only to nurses; (4) the triage time is the registration time (admitted_at and the triage event's occurred_at), not asked in the form; (5) after saving, the app navigates to /patients/<generated code>. Scope: protected page /patients/new and POST /api/patients; uses the existing patients table (no migration) and, in the same transaction, an initial triage event (source \"initial\", previous_level null, created_by the current user). Validation: age 0–130, sex female/male/other, triage level 1–5 shown as Triage I–V, 422 without echoing values. Reuse Button, Card and TriageLevelBadge, tokens only, lucide-react icons, Spanish and English texts, glossary terms. Out of scope: patient list content (US-02), readings (US-03), patient detail content (US-05)."

## Clarifications

### Session 2026-11-20

- Q: When the system picks the next patient code, should it count up from the highest existing code, or fill the lowest unused number from PAT-007 up? → A: Highest existing `PAT-<digits>` number + 1, never below 7; gaps are not filled, so a code is never reused.
- Q: If a registration request contains a field the system doesn't expect (for example a client-sent patient code), should it reject the request or ignore the field? → A: Reject with 422 naming the unexpected field (value not echoed); nothing is stored.
- Q: When a signed-in doctor opens /patients/new directly, what should they see? → A: The page stays open and shows a translated "only nurses can register patients" message with a link back to the patient list, and no form.
- Q: When the registration form first opens, should a triage level be pre-selected, or must the nurse pick one explicitly? → A: Nothing is pre-selected; the nurse enters the level from the triage already done by a clinician (the app does not assess triage). Triage level and sex start empty and are required.
- 2026-11-20 (change request from the manual check): the name label is just "Nombre" / "Name" instead of "Nombre (ficticio)" / "Name (fictitious)", because the hint "No uses datos reales." / "Do not use real data." already says the name must be fictitious. The hint is unchanged (AC7, FR-011).

## User Story *(mandatory)*

**Story ID**: US-01

**Type**: Functional (baseline)

**Story**: As a nurse, I want to register a triaged patient with their initial triage level, so that the system starts monitoring them.

**Depends on**: TS-03 (tables and migrations), TS-06 (authentication), TS-12 (UI foundation), TS-13 (client routing). All merged.

### Acceptance Criteria

<!-- Each criterion must be testable. qa-tester writes at least one test per criterion. -->

1. **AC1 — Nurse registers a patient**: **Given** a signed-in nurse, **When** they send a valid registration (name, age, sex, triage level), **Then** the system answers "created" with the new patient's patient code, name, age, sex, triage level, `status` = `active` and `admitted_at`; the patient is stored with `status` = `active`; **and** exactly one triage event is stored for that patient with `source` = `initial`, `previous_level` empty, `new_level` equal to the chosen triage level, `created_by_id` equal to the nurse, and `occurred_at` equal to the patient's `admitted_at`.
2. **AC2 — System-generated patient code, demo codes reserved**: **Given** any set of existing patients, **When** a patient is registered, **Then** the system assigns the patient code itself in the format `PAT-NNN` (at least three digits): `PAT-007` when no registered code exists above `PAT-006`, otherwise the next number after the highest existing `PAT-NNN` code; the codes `PAT-001` to `PAT-006` are never assigned; **and** a patient code sent by the client is not accepted (the request is rejected as invalid).
3. **AC3 — One retry on a code conflict**: **Given** two registrations that would receive the same patient code at the same time, **When** saving the second one hits the unique-code conflict, **Then** the system computes the next code again and retries once; if the retry succeeds the patient is created with a different code; if it also conflicts the system answers "conflict" with a fixed, safe message and stores neither a patient nor a triage event.
4. **AC4 — All or nothing**: **Given** a registration, **When** the patient or the initial triage event cannot be saved, **Then** neither is stored (no patient without its initial triage event, no orphan triage event).
5. **AC5 — Only nurses may register**: **Given** a registration request, **When** it is sent signed out (no or invalid token), **Then** the answer is 401; **When** it is sent by a signed-in doctor, **Then** the answer is 403; in both cases nothing is stored.
6. **AC6 — Input validation without echoing values**: **Given** a registration with a missing field, an empty or whitespace-only name, a name longer than 100 characters, an age that is not a whole number or outside 0–130, a sex other than `female`, `male` or `other`, a triage level that is not a whole number from 1 to 5, or an unknown extra field, **When** it is sent, **Then** the answer is 422, it names only the field(s) and the kind of problem, it never repeats the submitted values, and nothing is stored.
7. **AC7 — Registration page**: **Given** a signed-in nurse, **When** they open `/patients/new`, **Then** they see a registration form inside a Card with: a required name field labeled "Nombre" ("Name" in English) with the hint "do not use real data"; an age field; a sex choice (female / male / other); and a triage level choice showing the five levels as "Triage I" to "Triage V" with the shared triage level badge; there is no field for the patient code or the triage time.
8. **AC8 — Form checks before sending**: **Given** the registration form, which opens with no triage level and no sex pre-selected, **When** the nurse submits it with a required field empty (including no triage level or no sex chosen) or an age outside 0–130, **Then** the form shows a message next to each invalid field, does not send the request, and keeps what was typed.
9. **AC9 — Navigation after saving**: **Given** a valid form, **When** the nurse submits it and the system answers "created", **Then** the app navigates to `/patients/<generated patient code>` (the patient detail page).
10. **AC10 — Failed save keeps the form**: **Given** a submitted form, **When** the system answers with a validation error, a conflict, a server error or no answer (network failure or timeout), **Then** the page stays on the form, keeps what was typed, shows a fixed, translated error message (never the raw server text), and the submit button is usable again; while a save is in progress the submit button is disabled so the patient cannot be registered twice by double-clicking.
11. **AC11 — "Register patient" button for nurses only**: **Given** the patient list page, **When** a nurse is signed in, **Then** a "Register patient" button with an icon is shown and opens `/patients/new`; **When** a doctor is signed in, **Then** the button is not shown.
12. **AC12 — Page protected and role-aware**: **Given** `/patients/new`, **When** a signed-out visitor opens it, **Then** they are redirected to the login page (existing protected-route behavior); **When** a signed-in doctor opens it, **Then** they see a translated message that only nurses can register patients and a link back to the patient list, and no form.
13. **AC13 — Address ranks above the patient detail address**: **Given** the app routes, **When** `/patients/new` is opened, **Then** the registration page is shown, not the patient detail page or the not-found page.
14. **AC14 — Spanish by default, English switch**: **Given** the registration page and the "Register patient" button, **When** the language is Spanish (default) or English, **Then** every label, hint, option, button and message is shown in that language using glossary terms, and switching language does not clear what was typed.

### Out of Scope

- The content of the patient list (US-02): this story only adds the nurse-only "Register patient" button to the existing patient list page.
- Readings and scoring (US-03); no reading is created at registration, so a new patient has no NEWS2 score yet.
- The content of the patient detail page (US-05): this story only navigates to its address.
- Editing, discharging or deleting a patient, or changing the triage level after registration.
- Asking for or editing the triage time; it is always the registration time.
- Any database migration: the existing `patients` and `triage_events` tables are used as they are.
- Detecting whether a name is real; the form only warns, it does not check.

### Edge Cases

- **Gaps in the codes** (for example `PAT-007` and `PAT-009` exist, `PAT-008` does not): the next code is after the highest existing one (`PAT-010`); gaps are not filled, so a code is never reused.
- **Codes that do not follow `PAT-NNN`** (for example a hand-inserted `TEST-1`) are ignored when computing the next code.
- **Only demo patients exist** (`PAT-001` to `PAT-006`), or no patient exists at all: the first registered code is `PAT-007`.
- **Past `PAT-999`**: the number keeps growing (`PAT-1000`), within the 20-character limit of the patient code.
- **Two nurses register at the same moment**: the one-retry rule (AC3) gives each a different code; if the retry also conflicts, the nurse sees a translated "please try again" message and nothing is stored.
- **Name with spaces around it**: leading and trailing spaces are removed before checking and saving; a name made only of spaces is invalid.
- **Age sent as text or with decimals** (for example `"40"` or `40.5`), or triage level `0` or `6`: rejected with 422, values not echoed.
- **Session expires while the form is open**: the save gets a 401 and the existing session-expiry handling sends the nurse to the login page.
- **A doctor types `/patients/new`** directly: no form is shown (AC12), and the server still refuses with 403 if a request is sent another way.
- **The patient detail page for the new code** shows only its current placeholder until US-05; the navigation itself is what this story checks.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST offer a registration operation (`POST /api/patients`) that creates one patient from a name, an age, a sex and a triage level, and answers "created" (201) with the patient's patient code, name, age, sex, triage level, `status` and `admitted_at`; the internal `patient_id` MUST NOT be returned.
- **FR-002**: The registration MUST require a signed-in user (401 otherwise) whose role is `nurse` (403 for any other role, including `doctor`).
- **FR-003**: The system MUST generate the patient code as `PAT-` followed by a number of at least three digits: one more than the highest number among existing patient codes of the form `PAT-<digits>`, and never less than 7, so `PAT-001` to `PAT-006` (the demo patients) are never assigned. The client MUST NOT be able to choose or send the patient code.
- **FR-004**: If saving fails because the generated patient code already exists, the system MUST compute the code again and retry exactly once; if the retry also fails on the code, it MUST answer 409 with a fixed, safe message.
- **FR-005**: The patient and its initial triage event MUST be saved together, all or nothing. The triage event MUST have `source` = `initial`, `previous_level` empty, `new_level` = the chosen triage level, no NEWS2 score, `created_by_id` = the signed-in nurse, a fixed `reason` stating it is the initial triage at registration, and `occurred_at` equal to the patient's `admitted_at`.
- **FR-006**: `admitted_at` and the triage event's `occurred_at` MUST be set by the system to the registration time; neither is accepted from the client.
- **FR-007**: The new patient MUST be saved with `status` = `active`, so the existing simulator picks it up like any other active patient.
- **FR-008**: The system MUST validate the request: `name` required, trimmed, 1–100 characters; `age` a whole number 0–130; `sex` one of `female`, `male`, `other`; `triage_level` a whole number 1–5; no other fields allowed. Any failure MUST answer 422 naming only the field and the kind of problem, never repeating the submitted values, and MUST store nothing.
- **FR-009**: Error answers (401, 403, 409, 422, and 503 when the database is unavailable, as in the existing auth endpoints) MUST use fixed, safe messages that reveal no internal details (no stack traces, database errors or submitted values).
- **FR-010**: The app MUST provide a protected page at `/patients/new`, registered inside the existing protected route group, that ranks above `/patients/:identifier`.
- **FR-011**: For a signed-in nurse, the page MUST show a form inside the shared Card with: name (required; label "Nombre" / "Name"; hint "do not use real data", which states that the name must be fictitious), age, sex (female / male / other) and triage level (five options shown as "Triage I" to "Triage V" with the shared TriageLevelBadge). It MUST NOT ask for the patient code or the triage time. No triage level and no sex MAY be pre-selected when the form opens: the nurse enters the level from the triage already done by a clinician, and both fields are required.
- **FR-012**: The form MUST check required fields and the age range before sending, show a message next to each invalid field, and not send an invalid form.
- **FR-013**: The submit action MUST use the shared Button, be disabled while a save is in progress, and on "created" the app MUST navigate to `/patients/<patient code>` from the answer.
- **FR-014**: On a 409, 422, 5xx or network/timeout failure, the form MUST stay filled in and show a fixed, translated error message; on a 401 the existing session-expiry handling applies.
- **FR-015**: For a signed-in doctor, `/patients/new` MUST show a translated "only nurses can register patients" message with a link back to the patient list, and no form.
- **FR-016**: The patient list page MUST show a "Register patient" button (shared Button, with a `lucide-react` icon) that opens `/patients/new`, only when the signed-in user's role is `nurse`. It MUST be added as a small mounted component so US-02 can keep it when it replaces the page body.
- **FR-017**: Every UI text in this story MUST be in Spanish by default and English with the language switch, come from the translations file, and use glossary terms; the glossary MUST gain the new UI texts (register, the form fields and the role message) in the same PR.
- **FR-018**: All styling MUST use the existing design tokens only (no raw colors), all icons MUST come from `lucide-react` and be decorative, and the existing raw-color and contrast guard tests MUST keep passing.
- **FR-019**: Automated tests MUST cover the registration endpoint (success, code generation including the demo-code reservation and gaps, the one retry, all-or-nothing, 401/403, each 422 case without echoed values) and the page (nurse form, doctor message, client checks, navigation after saving, failed save, button visibility, route ranking, both languages).
- **FR-020**: The patient code rule (system-generated, next after the highest, never `PAT-001` to `PAT-006`, one retry) MUST be recorded as a new decision (D-47) in `docs/DECISIONS.md`, and `docs/BACKLOG.md` and `docs/PROJECT_STATUS.md` MUST show US-01 as done when the story is finished.

### Key Entities *(include if feature involves data)*

- **Patient** (existing `patients` table, unchanged): a synthetic triaged patient with a system-generated patient code, a fictitious name, age, sex, current triage level, `admitted_at` (the registration time) and `status` (`active` at registration).
- **Triage event** (existing `triage_events` table, unchanged): the patient's initial triage level, recorded at registration with `source` = `initial`, no previous level, no NEWS2 score, the registering nurse as creator and the registration time as `occurred_at`.
- **User** (existing): the signed-in clinician; only the `nurse` role may register.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A nurse can register a patient from the patient list in under 1 minute, with 4 fields to fill in and no patient code or time to type.
- **SC-002**: 100% of registered patients have exactly one initial triage event matching their triage level and registration time; 0 patients exist without one.
- **SC-003**: 0 registrations ever receive a code from `PAT-001` to `PAT-006` or a code already used, across the test cases (empty table, demo patients only, gaps, non-`PAT` codes, simulated conflict).
- **SC-004**: 100% of registration attempts by doctors or signed-out callers are refused (403 / 401) and store nothing.
- **SC-005**: 100% of invalid inputs in the test cases are refused with 422 and 0 error answers contain a submitted value.
- **SC-006**: 100% of the texts on the registration page and the button appear in Spanish by default and in English after switching; 0 raw colors are added (guard test passes).
- **SC-007**: All existing backend and frontend tests still pass, and every acceptance criterion has at least one automated test.

## Assumptions

- "Next free" means one more than the highest existing `PAT-<digits>` number (minimum 7); gaps are not filled, so a code is never reused even after deletions (confirmed in Clarifications, 2026-11-20). This is the simplest rule that never collides with the demo codes.
- An unknown extra field in the request (including a client-sent patient code) is rejected with 422 rather than silently ignored, so the client can never choose the code (confirmed in Clarifications, 2026-11-20).
- The initial triage event's `reason` is a fixed English text (for example "Initial triage at registration"), since the column is required and no vital signs produced the level; the triage level comes from the nurse's professional classification (GLOSSARY §1.1).
- The fictitious-name rule is enforced by the hint only; the app cannot verify that a name is not real (constitution Principle VI is met by policy and synthetic demo data).
- The name keeps the existing 100-character limit of the `patients.name` column.
- The existing frontend API client and its 401 session-expiry handling (TS-06, TS-13) are reused for the save request; the user's role comes from the existing signed-in user data (`GET /api/me`).
- Adding the nurse-only button to `PatientListPage` (a TS-13 placeholder) counts as mounting a component, which the constitution (Principle III) allows; US-02 keeps the mounted button when it replaces the page body.
- Until US-05, the patient detail page reached after saving shows only its current placeholder; that is expected.
- No migration is needed: the `patients` and `triage_events` tables from TS-03 already hold every field this story writes.
